## Definition

**v2.1 is the complete replacement of Canon's custom coordination layer with Claude Code's native agent orchestration primitives.**

The coordination layer was Canon's custom state machine — `drive_flow`, flow YAML files, wave events, message channels, consultation executor, fragment inclusion system. It was built before Claude Code had multi-agent coordination. Now that Claude Code ships native multi-agent primitives, the custom layer is overhead. v2.1 deletes it.

**What v2.1 is:**

- The orchestrator reads a synthesized runbook (produced by the planner per build) and spawns agents as sequential subagents via the `Agent` tool
- Parallel execution within a step uses Claude Code native teams (`TeamCreate`/`TaskCreate`/`TaskList`) when the architect's `task-dag.yaml` has 2+ root tasks
- Canon's value stays entirely in its MCP tools: 58 principles, knowledge graph, drift tracking, review tooling, workspace/journal, artifact contracts, hooks
- The `CANON_AGENT_TEAMS_MODE` feature flag gates the new path during migration

**What v2.1 is not:**

- Complete. The soak period validated the transition; v2.1 finishes when the legacy code is deleted and the flag is removed.
- A rewrite of Canon's intelligence layer. Principles, drift, knowledge graph, and review tools are unchanged.

**Architectural precision — two distinct execution primitives:**

| Primitive | What it is | When Canon uses it |
|-----------|------------|-------------------|
| Sequential subagent spawns | The `Agent` tool, called once per runbook step | Research → Design → Implement → Review → Ship — each step is one subagent call |
| Native teams | `TeamCreate` + `TaskCreate` + `TaskList` — Claude Code built-in primitives | Parallel implementation when architect produces a `task-dag.yaml` with 2+ root tasks |

These are not Canon-implemented tools. They are Claude Code built-in primitives that the orchestrator calls directly. The orchestrator follows the protocol described in CLAUDE.md.

## DAG Validation

The DAG execution path allows the architect to declare parallel task execution via `task-dag.yaml`. Here is how to exercise it.

### What the DAG path is

When the architect produces a `task-dag.yaml` alongside task plans, the orchestrator uses it for parallel dispatch:

1. **Architect** produces `task-dag.yaml` at `${WORKSPACE}/plans/${slug}/task-dag.yaml` alongside individual task plan files
2. **Orchestrator** detects the file after the architect step, validates it with `dag-validator.ts`
3. **Orchestrator** calls `TeamCreate` to create a team, then `TaskCreate` for each DAG node with full enrichment payloads in the task description
4. **Orchestrator** spawns N worker engineers via `Agent({ team_name: "canon-{slug}", ... })`
5. **Workers** pull tasks via `TaskList`, claim with `TaskUpdate`, work, mark complete
6. **Orchestrator** merges worktrees sequentially after all tasks complete, then runs review → ship

### What the DAG path is NOT

The DAG is not executed by Canon code. `TeamCreate`, `TaskCreate`, and `TaskList` are Claude Code built-in primitives. The orchestrator follows the protocol in CLAUDE.md under "DAG Execution Protocol" when it detects a `task-dag.yaml`. No Canon code reads or processes the DAG automatically — `dag-validator.ts` exists as a utility, but nothing calls it until the orchestrator reads the file manually.

### How to exercise it

Run any build with a design step and multiple separable implementation tasks. The architect's DAG trigger condition (from `agents/architect.md`):

> Produce a `task-dag.yaml` for multi-task designs (2+ tasks). Never for single-task designs.

Concrete test: request a feature that requires changes to both a data layer and a UI layer. The architect should produce two tasks with no dependency between them. The orchestrator should create a team with two workers running in parallel.

### Current state

The DAG path was exercised in soak run #19 (`p0-composite-mcp-tool`) with 3 tasks in 2 waves (wave 1 parallel, wave 2 sequential). The `dag-validator.ts` utility exists but the SubagentStop hook that would auto-inject DAG context into the orchestrator is not yet shipped (v2.1c above).

## Target Architecture

This is the end state when v2.1 is complete.

### What Canon is

Canon is Claude's intelligence toolkit for principled software development. It provides:

1. **Principles** — 58 built-in rules, strong-opinions, and conventions. Agents query them per file via `get_principles`. Drift reports surface violations over time.
2. **Knowledge graph** — static analysis of the codebase: import/export relationships, blast radius, semantic search, file summaries. Agents query it to understand what they are touching.
3. **Runbook orchestration** — the planner synthesizes a per-build runbook from a canonical step vocabulary. The orchestrator executes it step by step, calling Canon MCP tools to compose context before each agent spawn.
4. **Artifact contracts** — every agent step declares what it produces. The workspace + journal system tracks those contracts. `verify_completion` enforces them at build end.
5. **Review + quality gates** — `write_review`, `store_pr_review`, `show_pr_impact`, `review_code` provide structured review artifacts. 12 lifecycle hooks enforce quality constraints at the tool call level.
6. **History + learning** — build history, cross-run analysis, transcript capture, and agent metrics feed the learner. The learner proposes principle and prompt improvements from observed patterns.

### What Canon is not

- A coordination layer. Sequential steps are `Agent` tool calls. Parallel steps are `TeamCreate`/`TaskCreate`. Both are Claude Code primitives.
- A flow state machine. Flow YAML, wave events, message channels, fragment composition — all deleted in v2.1b.
- A prompt pipeline. Context composition is direct MCP tool calls before each spawn, not a 9-stage pipeline.

### The orchestration model

```
User request
  → Orchestrator classifies intent
  → Spawns planner (Agent tool)
      → Planner produces planning-brief.md + runbook.md
      → Iterates with user until approval
  → init_workspace — creates workspace + journal
  → For each runbook step:
      → resolve_agent_skills — preloads agent context
      → get_context (or targeted MCP tools) — composes enrichment payload
      → Agent tool — spawns subagent (sequential step)
        OR
      → TeamCreate + TaskCreate + Agent (workers) — parallel step via native teams
      → Verify artifacts at declared paths
      → log_step completion
  → verify_completion
  → Shipper creates PR
```

### What stays forever

These are Canon's durable differentiators — independent of any coordination layer:

| Layer | What | Why it stays |
|-------|------|-------------|
| 58 principles | Rules, strong-opinions, conventions | The intellectual core. These encode what good software development looks like. |
| Knowledge graph | `codebase_graph`, `graph_query`, `semantic_search`, `get_file_context`, `get_context` | Agents cannot reason about what they do not understand. The KG gives them structural understanding of the codebase. |
| Drift tracking | `get_drift_report`, `get_compliance`, confidence decay | Principle compliance degrades over time without measurement. Drift keeps it visible. |
| Runbook orchestration | Planner synthesis, `init_workspace`, `log_step`, `verify_completion` | Structured builds produce predictable artifacts. Ad-hoc builds do not. |
| Agent definitions | 10 specialist agent types with tailored tools, rules, permissions, and memory | Each agent is optimized for its role. A planner is not an engineer. |
| Review + PR tools | `write_review`, `store_pr_review`, `show_pr_impact` | Structured reviews are evidence. Structured evidence accumulates into patterns. |
| Hooks | 12 across 4 lifecycle events | Hard enforcement of Canon invariants at the tool call level. L1 rules are behavioral; hooks are mechanical backstops. |
| Learning loop | Learner agent, `store_summaries`, history tools | Canon improves from every interaction. Principles, prompts, and synthesis patterns all have feedback channels. |
