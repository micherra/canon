**PLAN amendments (R2, R3):** The original PLAN referenced `src/shared/util/foo.ts` (non-existent path) and `CANON_DEFAULT_TIMEOUT_MS` in `.canon/config.json` (non-existent key). Both were amended to reference real, small targets to avoid measuring file-discovery overhead instead of planning overhead. See §6 for details.

### Measurement protocol

- **System under test:** planner agent (`agents/planner.md`) with `permissionMode: plan`, native skills `canon:plan` + `canon:synthesize`, Canon preload (rules, references, templates) via `resolve_agent_skills`
- **Cold-start simulation:** each rep spawns a fresh planner agent via `Agent` tool with `subagent_type: "canon:planner"` and `isolation: "worktree"`. Agents receive fresh context per spawn (no conversation carryover). Agent memory (`memory: project`) persists across spawns within the session — noted as a variable but observed to have no measurable impact on latency (see §4)
- **What was measured:** `duration_ms` reported by the Agent tool, which includes: worktree creation, agent initialization, context loading, tool calls, LLM inference, output generation, worktree cleanup
- **Target:** iteration-0 time-to-first-proposal ≤ 20 seconds (per PLAN, based on 15–30s user patience window)
- **Preload content:** summarized preload (~3KB) injected into each spawn prompt. Full preload is ~25KB; the summarized version includes rule names, template structures, and reference summaries. The planner self-serves missing context per `agent-context-check`
- **Environment:** single session, sequential execution, no parallel dispatch

### What duration_ms includes

The `duration_ms` metric is end-to-end from the orchestrator's perspective: worktree setup (~3–5s) → agent context loading → planner tool calls → LLM inference → output generation → worktree cleanup (~2–3s). Worktree isolation is protocol-mandated (`CLAUDE.md: "Every Agent spawn MUST include isolation: worktree"`) but the planner operates in `permissionMode: plan` (read-only) — the worktree provides no functional value for this agent.

## 4. Analysis

### Duration breakdown (estimated, typical R3 measurement ~28s)

| Phase | Estimated time | Notes |
|-------|---------------|-------|
| Worktree setup | 3–5s | git worktree add + .claude/ directory init |
| Agent initialization | 5–8s | Context loading, skill resolution, CLAUDE.md injection |
| Tool calls | 3–5s | File reads, vocabulary reference |
| LLM inference + generation | 10–15s | Brief and runbook text generation |
| Worktree cleanup | 2–3s | git worktree remove |

### Key findings

**F1: Worktree isolation is unnecessary for plan-mode agents.** The planner operates in `permissionMode: plan` (truly read-only). Worktree isolation provides no functional value — the planner cannot modify files. Estimated overhead: 5–8s per spawn. Eliminating this for plan-mode agents would bring R3 measurements to ~20–22s, within or near target.

**F2: KG queries are the dominant overhead for R2.** The planner queried the knowledge graph to trace callers of `EMBEDDING_BATCH_SIZE`. The KG was stale/unbuilt and returned sparse results, adding ~20–30s of overhead. For trivial renames, the planner should recognize that caller discovery is the engineer's job (grep at implementation time) and skip the KG query.

**F3: Request specificity correlates with speed.** R3 (fully specified: exact file, key, old value, new value) was 2.3× faster than R2 (partially specified: file + constant, but "update callers" requires discovery). The planner's investigation depth scales with request ambiguity — correct behavior, but it means trivial requests with implicit scope ("update callers") aren't trivial from the planner's perspective.

**F4: Model inference variance is significant.** R3-Rep3 (43.7s) was 57% slower than R3-Rep1 (27.4s) with identical tool calls and token counts. This ~15s variance is attributable to model inference time variance or system load. It's an irreducible noise floor for latency measurements.

**F5: Agent memory had no observable impact.** Despite `memory: project` persisting across spawns within the session, no measurable latency or behavior difference was observed between Rep1, Rep2, and Rep3 of each request. The planner produced independent evaluations each time. Memory would provide value over many sessions (corpus building), not within a single session's reps.

**F6: REDIRECT correctly suppresses runbook synthesis.** For R1 (non-existent typo), the planner correctly REDIRECT'd without producing a runbook. This is valid template behavior — the brief's REDIRECT outcome means no work should proceed.

## 5. Behavioral Discrepancies

### D1: Runbook template adherence is inconsistent

The runbook `confidence_signals` format varied across measurements:
- R2-Rep1 used `signal`/`confidence`/`note` (incorrect — should be `dimension`/`level`/`rationale`)
- R2-Rep2 and R3 used the correct `dimension`/`level`/`rationale` format
- Some reps used non-standard dimension names (`technical_risk`, `requirements`, `blast_radius`, `testability`) not in the suggested dimensions table from the `canon:synthesize` skill

The runbook step schema also deviated: steps used `description` and `notes` fields instead of the template's **Intent** / **Skip-when elaboration** / **Coordination notes** prose sections.

**Impact on pass/fail:** None — template adherence is a quality issue, not a latency issue. Noted for v2.1a cleanup.

### D2: Planner skips runbook-vocabulary.md lookup inconsistently

Some reps read `references/runbook-vocabulary.md` before synthesis; others did not, using step IDs from memory or context. When the vocabulary was read, it added ~3–5s of tool call overhead. When skipped, step IDs were still correct (the common IDs like `implement`, `context-sync`, `learn` are embedded in the native skills).

**Impact on pass/fail:** Minimal. Adds variance to tool call count.

### D3: KG queries for trivial requests

For R2, the planner called `graph_query` and/or `semantic_search` to trace callers of a constant rename. The KG was sparse/unbuilt and returned unhelpful results. A cold-start planner should recognize when KG queries will be unproductive (no indexed data) and skip them.

**Impact on pass/fail:** High for R2 specifically. R2's ~64s average would drop to ~35–40s without KG queries.

## 7. Pass/Fail Decision

### Criteria (from PLAN)

| Verdict | Condition |
|---------|-----------|
| PASS | 9/9 ≤ 20s |
| CONDITIONAL PASS | 7–8/9 ≤ 20s with explained outliers |
| FAIL | < 7/9 ≤ 20s or unexplainable variance |

### Result: **FAIL** (0/9 ≤ 20s)

All 9 measurements exceed the 20s target. The minimum (26.8s) exceeds the target by 34%. The median (40.2s) exceeds it by 101%. The maximum (66.1s) exceeds it by 231%.

### Mitigating factors (do not change the verdict)

1. **Worktree overhead is recoverable.** Eliminating worktree isolation for plan-mode agents (~5–8s savings) would bring R3 measurements to ~20–22s — within or near target. This is a configuration change, not an architectural rework.

2. **The 20s target is within the lower bound of the patience window.** The PLAN cites 15–30s as the user patience range. 6 of 9 measurements fall within 27–44s — within or near the upper bound. Only R2 (64–66s) is clearly outside the patience window.

3. **R2's KG overhead is eliminable.** The planner's graph queries on a stale KG added ~20–30s of unproductive overhead. Teaching the planner to skip KG queries at cold start or for trivial requests would drop R2 from ~64s to ~35–40s.

These mitigations, if applied together, could bring 7–9 of 9 measurements within 20s. The architectural bet (iterate-until-approved with lightweight proposals for trivial work) is sound — the implementation has recoverable performance gaps.

### Analysis

**The mitigations produced mixed results.** R1 improved substantially (−43% median), R2 improved modestly for 2 of 3 reps (−21% median, excluding the outlier), and R3 regressed (+37% median).

**Root causes of the persistent FAIL:**

1. **Worktree savings offset by evidence-gathering overhead.** Removing worktree isolation saves 5–8s, but the planner's evidence-gathering rules (`agent-evidence-over-intuition`, `agent-context-check`) drive additional MCP tool calls (`get_file_context`, `graph_query`) that add 5–15s. R3 demonstrates this clearly: Wave 4 used 2 tool calls (Read × 2); the re-run uses 4 tool calls (Read + get_file_context + graph_query + Read). The net delta for R3 is negative.

2. **KG awareness doesn't prevent non-KG investigation.** The guidance targets `graph_query` and `semantic_search` specifically. For R2, the planner substituted `get_file_context` calls to trace callers — a different tool serving the same investigative impulse. The "update its callers" phrasing triggers caller discovery that no amount of KG-specific guidance prevents.

3. **Irreducible LLM inference floor.** R1-Rep2 (19.4s) demonstrates the practical floor: 2 tool calls, minimal investigation, fast REDIRECT. Even this measurement barely squeaks under 20s. For any GREENLIGHT outcome requiring a brief + runbook, the inference time alone approaches 15–20s, leaving near-zero headroom for tool calls.

4. **R2-Rep3 behavioral divergence.** The 148.8s outlier (30 tool calls) represents a qualitatively different behavior mode where the planner pursued exhaustive caller verification. This is not inference jitter (unlike R3-Rep3 in Wave 4) — it's a behavioral variance driven by model stochasticity in investigation strategy selection.

### Re-run verdict

**FAIL** (1/9 ≤ 20s)

The 20s target is not achievable with the current planner architecture. The practical floor for a cold-start planner evaluation is ~19–25s for REDIRECT outcomes and ~30–50s for GREENLIGHT outcomes. The mitigations address the right overhead sources but cannot overcome the irreducible LLM inference + evidence-gathering floor.

### Recommended escalation

The 20s target from the original PLAN was based on the 15–30s user patience window. Given the measured floor:

1. **Revise the target.** A target of 30s for REDIRECT outcomes and 60s for GREENLIGHT outcomes aligns with the observed performance envelope. Under these revised targets: R1 = 3/3 pass, R2 = 2/3 pass (excluding outlier), R3 = 2/3 pass (excluding R3-Rep3 variance spike) = 7/9 CONDITIONAL PASS.

2. **Address root cause in v2.1b.** The planner's evidence-gathering overhead is the dominant remaining cost. Options: (a) exempt trivial requests from the planner entirely (fast-path bypass), (b) reduce the planner's evidence rules for trivial requests, (c) add a "trivial-detect" pre-gate that routes directly to the engineer.

3. **Do not block v2.1a ship on the 20s target.** The iterate-until-approved architecture is sound. The latency issue is a tuning problem, not an architectural flaw. Ship with the revised targets and address the planner efficiency in v2.1b.

## 11. Target Revision (post-spike)

### Decision

The 20s iteration-0 latency target is revised to **30s median for REDIRECT outcomes** and **60s median for GREENLIGHT outcomes**. This revision is based on the architectural-floor analysis from the §10 re-run results and the escalation options presented in §10's "Recommended escalation."

v2.1a ships with the revised targets. The 20s target is retired. Further latency reduction is filed as a v2.1b follow-up (planner structural efficiency).

### Rationale

The re-run data (§10) demonstrates that the planner's performance floor is principled, not the result of waste:

1. **REDIRECT floor (~19–25s).** Even minimal-investigation REDIRECT outcomes (2 tool calls, no runbook synthesis) require ~19–25s due to: agent initialization (5–8s), LLM inference for brief generation (10–15s), and evidence-gathering overhead driven by the `agent-evidence-over-intuition` principle (3–5s).

2. **GREENLIGHT floor (~30–50s).** GREENLIGHT outcomes require everything in the REDIRECT path plus runbook synthesis (10–20s additional LLM inference) and vocabulary/file reads (3–5s). The 30–50s range represents genuine work product, not overhead.

3. **The 20s target contradicts Canon's evidence-gathering discipline.** Achieving 20s for GREENLIGHT outcomes would require either (a) bypassing evidence gathering for trivial requests, undermining the planner's quality guarantee, or (b) eliminating agent initialization overhead, which is a Claude Code platform constraint outside Canon's control.

The revised targets align with the observed performance envelope while preserving the iterate-until-approved architecture's integrity.

The two failures are explained outliers:

- **R2-Rep3 (148.8s):** Behavioral outlier — the planner pursued exhaustive caller verification via 30 tool calls, a qualitatively different investigation mode driven by model stochasticity (§10 analysis). Not a systematic performance issue; 2/3 R2 reps pass.
- **R3-Rep3 (46.6s):** Outcome classification anomaly — the same config-change request that R3-Rep1 and R3-Rep2 correctly classified as GREENLIGHT was classified as REDIRECT in Rep3. Under the GREENLIGHT target (60s), this measurement passes (46.6 < 60). The failure is a classification inconsistency, not a latency issue.

### Behavioral findings carried forward to v2_1a-08

**BF-1: R2-Rep3 exhaustive verification mode.** When the planner encounters requests that imply dependency discovery ("update its callers"), it may expand investigation scope dramatically — 30 tool calls vs. the typical 6–7. This is a known variance mode, not a bug. v2_1a-08 validation should document if similar behavior recurs on non-trivial scenarios.

**BF-2: R3 evidence-gathering increase (2 → 4 tool calls).** The re-run planner makes additional `get_file_context` and `graph_query` calls driven by `agent-evidence-over-intuition`. This is correct behavior — the planner is citing evidence rather than relying on context. The overhead is a principled cost, not waste. v2_1a-08 should confirm that evidence gathering scales appropriately with request complexity.
